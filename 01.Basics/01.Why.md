# Why MongoDB

- When should we choose MongoDB over relational databases.


## 1. MongoDB shines when your data is naturally a document

- There are two options. First we split our data across multiple tables and then aggregate them using joins. Or we store and read our data as a single unit.
- It makes more sense to store and retrieve our data as one unit.
- If your application primarily thinks: "Give me this entire object." rather than:"Join these 7 entities and calculate something across them."
- Documents are relatively self-contained

```json
{
  "name": "iPhone 17",
  "brand": "Apple",
  "price": 79999,
  "specifications": {
    "display": {
      "size": 6.3,
      "refreshRate": 120
    },
    "camera": {
      "main": "48MP",
      "front": "12MP"
    }
  },
  "variants": [
    {
      "color": "Black",
      "storage": "256GB",
      "price": 79999
    },
    {
      "color": "Blue",
      "storage": "512GB",
      "price": 89999
    }
  ]
}
```

- In MongoDB, this is basically one document. This entire thing is one product. Store and retrieve it as one unit.
- In a relational model, you might end up with:

```text
products
product_variants
product_specifications
product_cameras
```

## 2. Flexible schema, Highly variable document structure

- Imagine you're building a marketplace where sellers can sell: phones, cars, clothes, laptops, furniturte.
- Their attributes are completely different.
- With MongoDB, these can naturally live in the same collection.
- When your application changes its data structure frequently and you don't want every change to revolve around relational migrations.

```text
Product
 ├── phone attributes
 ├── car attributes
 ├── clothing attributes
 └── furniture attributes
```

## 3. MongoDB is excellent when you mostly retrieve aggregates

```json
{
  "_id": "post123",
  "author": {
    "id": "u123",
    "name": "John"
  },
  "content": "Hello world",
  "comments": [
    {
      "user": "Alice",
      "text": "Nice!"
    },
    {
      "user": "Bob",
      "text": "Great!"
    }
  ],
  "tags": ["mongodb", "backend"]
}
```
- Consider a social media post. If your application usually asks: Give me the post with its comments, author information and tags.
- MongoDB's document model fits this access pattern extremely well.

With Postgres, you'd commonly have and reconstruct the aggregate using joins.

```text
posts
users
comments
post_tags
tags
```
